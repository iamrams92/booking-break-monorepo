## ปัญหาและบริบท

ต้องการสร้างระบบจองตั๋วที่ใช้ฝึกและแสดงความเข้าใจด้าน Fullstack Engineering โดยเน้นความถูกต้องของการจองภายใต้การแข่งขัน การชำระเงิน การหมดเวลาจอง และการคืนตั๋วเข้าระบบ ระบบต้องรองรับงานสองลักษณะ ได้แก่ งานที่ลูกค้าเลือกที่นั่ง และงานที่ขายตั๋วตามจำนวน เช่น งานวิ่งหรืองานกิจกรรม

## ผลลัพธ์ที่ต้องการ

ผู้จัดงานสร้างและเผยแพร่งานได้ ส่วนลูกค้าค้นหาหรือเข้าถึงงาน เลือกที่นั่งหรือตั๋วตามรูปแบบงาน และทำรายการจองให้สำเร็จด้วยการชำระเงินภายในเวลาที่กำหนด ผู้จัดงานติดตามยอดและสถานะการจองผ่าน Dashboard อย่างง่ายได้

## ข้อกำหนดที่ยืนยันแล้ว

ข้อกำหนดต่อไปนี้รวบรวมจากคำขอและคำชี้แจงของผู้พัฒนา และได้รับการยอมรับสำหรับ change นี้แล้ว

- แบ่งบทบาทผู้ใช้เป็น Event Owner และ Customer
- Event Owner สร้าง Event พร้อมข้อความและรูปภาพ และเลือกโหมดงานได้ 2 แบบ: ระบุที่นั่ง หรือจำหน่ายตั๋วตามจำนวน
- ต้องมีผังจำลอง 3 สถานที่ ได้แก่ สนามกีฬาและเวที หอประชุม และโรงภาพยนตร์ โดยผังที่นั่งระบุที่นั่งได้ชัดเจน
- Customer จองตั๋วและต้องชำระเงินเพื่อให้การจองสำเร็จ หากไม่ชำระภายใน 15 นาที ตั๋วที่ถูกจองไว้ต้องกลับมาให้จองได้อีก
- Event Owner ดูข้อมูลอย่างน้อย ได้แก่ ยอดคงเหลือ จำนวนการจองสำเร็จ จำนวนรายการค้างชำระ และจำนวนรายการที่หมดเวลาจอง
- Event Owner แก้ไขข้อมูลที่มีผลต่อการจองได้เฉพาะระหว่างเป็น Draft; หลัง Publish แก้ได้เฉพาะรายละเอียดที่ไม่เกี่ยวข้องกับการจอง
- ผังสถานที่ทั้งสามใช้ซ้ำได้ และ Event Owner เลือกเปิด/ปิดหรือกันพื้นที่ในผังได้ เช่น กันพื้นที่สนามกีฬาไว้เป็นเวที
- ทุก Event ต้องมีความจุสูงสุด งานแบบระบุที่นั่งใช้จำนวนที่นั่ง ส่วนงานแบบบัตรใช้ max capacity และรองรับบัตรหลายประเภทพร้อมราคาแยกกัน เช่น VIP/Regular หรือระยะวิ่ง 5K/10K/21K
- เมื่อลูกค้าจอง ระบบแสดง QR Code สำหรับธุรกรรม ลูกค้าสแกนด้วยมือถือเพื่อเปิดหน้าธุรกรรม กรอกยอดเงินให้ตรงและยืนยันเพื่อจำลองการชำระเงินสำเร็จ ต้องมีวิธี bypass/mock สำหรับการทดสอบ
- ไฟล์ Event รองรับภาพนิ่งและ PDF ไม่รองรับ SVG, วิดีโอ หรือ GIF; จำกัดภาพไม่เกิน 10 MB และ PDF ไม่เกิน 50 MB; MinIO/S3-compatible storage ใช้จัดเก็บในทุก Environment
- Event Owner ผู้สร้าง Event เท่านั้นมีสิทธิ์ยกเลิก Event; booking ที่ชำระแล้วทั้งหมดเปลี่ยนตามลำดับ “รอคืนเงิน” → “กำลังดำเนินการคืนเงิน” → “คืนเงินแล้ว”
- บัญชี Event Owner และ Customer แยกประเภทและห้ามใช้ข้ามบทบาท
- หลัง Publish ล็อกข้อมูลที่เกี่ยวข้องกับการจอง อนุญาตแก้เฉพาะคำอธิบายและรูปภาพ
- ความจุที่ขายได้ลดตามพื้นที่นั่งที่ปิด; แบบตั๋วกำหนดความจุแยกประเภทได้ โดยผลรวมต้องไม่เกินความจุ Event
- ต้องกำหนดแนวทางทดสอบเพื่อแสดงว่าระบบและส่วนต่าง ๆ ทำงานตามที่ควร
- ใช้ Next.js และ Tailwind CSS สำหรับ Frontend, NestJS สำหรับ Backend และ PostgreSQL เป็นฐานข้อมูล
- ต้องเลือก CSS component ที่เรียบง่ายและเหมาะสม และใช้ lucide-icon แทน emoji เพื่อการตกแต่ง
- ใช้ S3-compatible storage ที่ระบุ MinIO สำหรับเก็บไฟล์รูปภาพ
- เริ่มงานด้วย change `001-initial-product` แล้วจึงเพิ่มความสามารถใน change ภายหลัง
- Agent ควรสื่อสารเป็นภาษาไทยเป็นค่าเริ่มต้น; Skill `translate` เป็นงาน Harness แยกจากผลิตภัณฑ์ 001 และใช้แปลเฉพาะ summary เป็นภาษาไทยเมื่อเรียกใช้

## ข้อเสนอขอบเขต MVP สำหรับพิจารณา

MVP ที่เสนอให้ทำเป็นเส้นทางใช้งานตั้งแต่ต้นจนจบ โดยคงความสามารถพื้นฐานที่ระบุไว้และตัดงานต่อยอดออก:

1. **เข้าใช้งาน:** สมัคร/เข้าสู่ระบบด้วยบัญชี BookingBreak หรือ Google แยกทาง Event Owner และ Customer; บัญชีหนึ่งใช้ข้ามบทบาทไม่ได้
2. **สร้างและเผยแพร่ Event:** Event Owner สร้าง Draft เลือกหนึ่งในผังสถานที่ตั้งต้นที่ใช้ซ้ำได้ หรือเลือกโหมดตั๋วตามจำนวน กำหนดประเภทและราคา รายละเอียด และไฟล์ภาพ/PDF แล้ว Publish; หลัง Publish แก้ได้เฉพาะคำอธิบายและรูปภาพ
3. **จองและชำระจำลอง:** Customer ดู Event ที่เผยแพร่ เลือกที่นั่งหรือประเภท/จำนวนตั๋ว สำรองได้ 15 นาที แล้วใช้ QR เปิดหน้าธุรกรรมบนมือถือ กรอกยอดที่ระบบคำนวณและยืนยัน ระบบจึงบันทึกการชำระจำลอง; มีช่องทาง bypass/mock สำหรับการทดสอบ
4. **ติดตามและจัดการ:** Event Owner ดู capacity/reserved, จำนวนคงเหลือ และ booking ตามสถานะ; Event Owner ผู้สร้างเท่านั้นยกเลิก Event ได้ และรายการที่ชำระแล้วเดินสถานะคืนเงินสามขั้นตามที่กำหนด การคืนเงินจริงอยู่นอก MVP
5. **ยืนยันความถูกต้อง:** UI และ API ทำงานร่วมกันจริง และทดสอบเส้นทางหลัก การหมดอายุ การกรอกยอดผิด การยืนยันซ้ำ การยกเลิก/สถานะคืนเงิน และการแข่งขันจองตาม baseline 100 คำขอต่อ inventory 20

ข้อเสนอนี้เน้นความครบของเส้นทางและ invariant สำคัญ ไม่รวมรายงานเชิงวิเคราะห์ขั้นสูง การเชื่อมต่อ payment provider จริง การคืนเงินจริง หรือการวัด performance/SLO แบบ production การเลือก CSS component ที่เหมาะสมให้กำหนดใน Specification หลังสำรวจตัวเลือกที่เข้ากับ stack โดยไม่เพิ่มความซับซ้อนเกินจำเป็น

## ขอบเขต

Intent นี้กำหนดขอบเขตเฉพาะระบบพื้นฐานตาม brief: UI ที่ผู้ใช้โต้ตอบได้จริงและ API ที่ทำงานได้จริงสำหรับ Event สองโหมด ผังสถานที่จำลองที่ใช้ซ้ำได้ การจองและ mock payment ผ่าน QR ภายในกรอบ 15 นาที Dashboard ขั้นต้น และการทดสอบส่วนสำคัญ โดยยังไม่จำเป็นต้องทำทุกความสามารถที่อาจมีในระบบจองตั๋ว งานส่วนเกินจากเส้นทางพื้นฐานให้พิจารณาแยกเป็น change ในอนาคต รายละเอียดเส้นทางและเกณฑ์การยอมรับจะจัดทำใน Specification หลังยอมรับ Intent นี้

## สิ่งที่ยังไม่รวมในขอบเขตที่ยืนยันแล้ว

- รายละเอียดเชิงเทคนิค เช่น โครงสร้างฐานข้อมูล API รูปแบบ transaction และการออกแบบ concurrency จะพิจารณาใน Specification และ Plan ไม่ถือเป็นการตัดสินใจแล้วใน Intent นี้
- การชำระเงินใน change นี้เป็นการจำลอง ไม่เชื่อมต่อผู้ให้บริการชำระเงินจริง
- ระบบคืนเงินจริง การโอนสิทธิ์ตั๋ว อีเมล และแอปมือถือยังไม่ได้ระบุเป็นส่วนของระบบพื้นฐาน

รายการเหล่านี้เป็นเพียงขอบเขตที่ยังไม่ได้ระบุ ไม่ใช่ข้อสรุปว่าจะตัดออกจากผลิตภัณฑ์ทั้งหมด

## ข้อจำกัด

- เป้าหมายโครงการคือ R&D/Portfolio ขนาดเล็กประมาณ 2–3 สัปดาห์ ให้ความสำคัญกับความถูกต้องและการเรียนรู้มากกว่าจำนวนฟีเจอร์ (เอกสาร Product Vision)
- แนวทางเทคโนโลยีที่ผู้พัฒนาระบุสำหรับ change นี้คือ Next.js, Tailwind CSS, NestJS, PostgreSQL, MinIO ผ่าน S3-compatible storage และ lucide-icon
- ต้องเลือก CSS component ที่เรียบง่าย แต่ยังไม่ได้ระบุชื่อ library
- การจองที่ยังไม่ชำระมีอายุ 15 นาที ตามคำขอผู้พัฒนา
- รองรับภาพนิ่งไม่เกิน 10 MB และ PDF ไม่เกิน 50 MB; ไม่รองรับ SVG, GIF หรือวิดีโอ; ชนิด raster ที่รับได้ให้กำหนดใน Specification
- ใช้ MinIO/S3-compatible storage ในทุก Environment ตามคำขอ แต่รูปแบบ Environment ยังต้องกำหนดใน Plan

## เกณฑ์ความสำเร็จ

เกณฑ์ต่อไปนี้เป็นข้อเสนอจากคำขอและต้องปรับให้ทดสอบได้ใน Specification:

- ผู้ใช้ในบทบาท Event Owner สร้าง Event แบบระบุที่นั่งและแบบตั๋วตามจำนวนได้
- ลูกค้าจองที่นั่งหรือตั๋วได้ และระบบแสดงความแตกต่างระหว่างการจองที่รอชำระกับการจองที่สำเร็จ
- ลูกค้าสแกน QR Code เพื่อเปิดธุรกรรม กรอกจำนวนเงินที่ถูกต้องและยืนยันแล้วได้รับผลการชำระเงินจำลอง; มีช่องทาง bypass/mock ที่ใช้ทดสอบได้
- เมื่อหมดเวลา 15 นาทีโดยยังไม่ชำระ ที่นั่งหรือตั๋วกลับมาเปิดให้จองได้ โดยไม่ทำให้จำนวนคงเหลือหรือสถานะผิดพลาดเมื่อมีผู้ใช้หลายรายดำเนินการพร้อมกัน
- Dashboard แสดงจำนวนคงเหลือและ reserved/capacity พร้อมจำนวนสำเร็จ ค้างชำระ และหมดเวลาจอง
- หลัง Publish ระบบอนุญาตแก้เฉพาะรายละเอียดที่ไม่กระทบการจอง; เมื่อมีการจองแล้ว Event ลบไม่ได้
- Event Creator เท่านั้นยกเลิกได้; booking ที่ชำระแล้วทั้งหมดเข้าสู่สถานะ “รอคืนเงิน” → “กำลังดำเนินการคืนเงิน” → “คืนเงินแล้ว” โดยไม่ถือว่าระบบดำเนินการคืนเงินจริงใน change นี้
- ภาพนิ่ง (ไม่เกิน 10 MB) และ PDF (ไม่เกิน 50 MB) ของ Event จัดเก็บผ่าน MinIO/S3-compatible storage ในทุก Environment; ปฏิเสธ SVG, GIF และวิดีโอ
- มีชุดทดสอบที่ครอบคลุมเส้นทางปกติและกรณีผิดพลาดสำคัญ รวมถึงการแย่งจอง การชำระเงินซ้ำ/ยอดไม่ตรง และการหมดเวลาจอง โดยรายละเอียดจะกำหนดใน Specification

## ข้อเสนอเป้าหมายทดสอบ concurrency

เนื่องจากยังไม่มีเป้าหมายโหลด ผู้ช่วยเสนอ baseline สำหรับ R&D เพื่อให้ตรวจสอบ invariant การขายเกินได้โดยไม่ตั้งเป้าระดับ production:

- ยิงคำขอจองพร้อมกัน 100 รายการไปยัง inventory เดียวที่มี 20 ที่นั่ง/ตั๋ว โดยทดสอบทั้งโหมดเลือกที่นั่งและโหมดจำนวน
- ผลที่คาดหวังคือมีรายการจองที่ถือครอง inventory ได้ไม่เกิน 20 รายการ ไม่มีที่นั่งเดียวกันถูกยืนยันซ้ำ ไม่มี capacity ติดลบ และสถานะคงเหลือถูกต้อง
- เพิ่มกรณีแข่งขันระหว่างการยืนยันชำระเงินกับการหมดอายุ และส่งการยืนยันชำระซ้ำ เพื่อยืนยันว่ารายการเดียวไม่ทำให้ตัดสิน inventory ซ้ำ
- ใช้ clock ที่ควบคุมได้ในการทดสอบอายุ 15 นาที เพื่อไม่ต้องรอเวลาจริง; ใช้ PostgreSQL จริงสำหรับ integration test ที่ตรวจ transaction/concurrency

ตัวเลข 100 คำขอและ inventory 20 เป็นเพียงข้อเสนอทดสอบเชิง correctness ไม่ใช่ SLO หรือคำกล่าวอ้างเรื่องความสามารถรองรับโหลดจริง หากผู้พัฒนาต้องการ load test เพื่อวัด throughput/latency ควรกำหนดจำนวนผู้ใช้พร้อมกัน ระยะเวลา และเป้าหมาย latency แยกต่างหาก

## สมมติฐาน

- bypass/mock payment ใช้สำหรับการทดสอบ; วิธีจำกัดการเปิดใช้และป้องกันการใช้จาก Customer ทั่วไปจะกำหนดใน Specification/Plan
- รายละเอียด Event ขั้นต่ำก่อน Publish จะกำหนดเป็นส่วนหนึ่งของ Specification เพื่อให้เส้นทาง MVP ใช้งานได้ครบ

## คำถามที่ยังเปิดอยู่

ไม่มีคำถามที่ขัดขวาง Intent นี้ ผู้พัฒนาได้ยอมรับขอบเขต MVP และ baseline concurrency 100 คำขอต่อ inventory 20 พร้อมยืนยันการแยกบัญชี, การจัดการสถานะคืนเงินแบบ Manual และชนิด/ขนาดไฟล์ตามข้อเสนอ

ขอบเขตและคำตอบข้างต้นได้รับการยอมรับแล้ว; Specification แยกต่างหากอยู่ระหว่างจัดทำเพื่อให้ผู้พัฒนาพิจารณาก่อนเริ่ม Implementation Plan.
