## เป้าหมาย MVP

ส่งมอบระบบแนวตั้งที่ UI ใช้งานโต้ตอบได้และ API ทำงานจริง ครอบคลุมการสร้าง/เผยแพร่ Event ทั้งแบบมีที่นั่งและแบบกำหนดจำนวน การจอง การชำระเงินจำลองผ่าน QR การหมดอายุ 15 นาที และ Dashboard ขั้นต้น โดยเน้นความถูกต้องของ inventory และสถานะ

## ผู้ใช้และสิทธิ์

### Event Owner

- สมัครและเข้าสู่ระบบได้ด้วยบัญชี BookingBreak หรือ Google Authentication
- ระบบบัญชี Event Owner และ Customer แยกจากกันโดยสิ้นเชิง ทั้งการจัดเก็บบัญชีและการยืนยันตัวตน ใช้ข้ามบทบาทไม่ได้
- สร้าง Event, บันทึก Draft, แก้ไข Draft และ Publish Event ของตนได้
- หลัง Publish แก้ไขได้เฉพาะคำอธิบายและรูปภาพ ไม่สามารถแก้ข้อมูลที่กระทบการจอง เช่น ราคา ประเภทตั๋ว ความจุ หรือผังที่นั่ง
- ดู Dashboard ของ Event ที่ตนเป็นผู้สร้าง
- ผู้สร้าง Event เท่านั้นยกเลิก Event นั้นได้
- เปลี่ยนสถานะคืนเงินของ booking ที่ชำระแล้วด้วยตนเอง ตามลำดับที่กำหนด; ไม่มีระบบเชื่อมโยงหรือทำงานอัตโนมัติ

### Customer

- สมัครและเข้าสู่ระบบได้ด้วยบัญชี BookingBreak หรือ Google Authentication
- ระบบบัญชี Customer แยกจากระบบบัญชี Event Owner โดยสิ้นเชิง ใช้ข้ามบทบาทไม่ได้
- เรียกดู Event ที่ Publish แล้ว เลือกที่นั่งหรือประเภทและจำนวนตั๋ว ทำ reservation และชำระเงินจำลองได้
- เข้าหน้าธุรกรรมจาก QR Code ด้วยอุปกรณ์มือถือ

### ข้อกำหนด authorization

- API ต้องตรวจบทบาทและ ownership ที่ฝั่ง server สำหรับทุกการกระทำที่เปลี่ยนข้อมูลหรือเปิดข้อมูลเฉพาะเจ้าของ Event; การซ่อนปุ่มใน UI อย่างเดียวไม่เพียงพอ
- Customer ห้ามเข้าถึงหรือเรียก action สำหรับ Event Owner และ Event Owner ห้ามใช้ Customer account/API ข้ามบทบาท
- การใช้ Google Authentication ต้องผูกตัวตนไว้ภายใน account realm ที่เลือก (Owner หรือ Customer) และห้ามการ login ครั้งเดียวสลับข้าม realm โดยปริยาย

## Event และ inventory

- Event เริ่มเป็น Draft ก่อน Publish และต้องมีข้อมูลที่จำเป็นต่อการแสดง Event, วัน/เวลาจัดงาน, โหมดการขาย, ราคา และ inventory ตามโหมดนั้น; รายการช่องข้อมูลบังคับแน่นอนเป็นคำถามเปิด
- มีโหมดการขาย 2 แบบ: (1) เลือกที่นั่งที่ระบุในผัง หรือ (2) เลือกประเภทตั๋วและจำนวนจาก capacity
- ทุก Event มีความจุสูงสุด
- แบบเลือกที่นั่งอ้างอิงผังสถานที่ตั้งต้นที่ใช้ซ้ำได้ 3 แบบ: สนามกีฬาและเวที, หอประชุม, โรงภาพยนตร์
- Event Owner เลือกเปิด/ปิดที่นั่งหรือพื้นที่ในผังได้ พื้นที่ปิดไม่อยู่ใน capacity ที่ขายได้; ที่นั่งหนึ่งตำแหน่งมี reservation ที่ยังถือสิทธิ์ได้ไม่เกินหนึ่งรายการ
- แบบกำหนดจำนวนรองรับหลายประเภท/โซน/ระยะทาง แต่ละประเภทมีราคาและ capacity ของตน ผลรวม capacity ประเภทต้องไม่เกินความจุ Event
- ราคาหรือ capacity ไม่ถูกเปลี่ยนหลัง Publish
- หลัง Publish ห้ามแก้ข้อมูลการจอง อนุญาตเฉพาะคำอธิบายและรูปภาพ
- Event ที่ Publish แล้วลบไม่ได้เมื่อมี reservation เกิดขึ้น; การยกเลิกเป็น action แยกจากการลบและทำได้โดย Event Owner ผู้สร้าง

## ไฟล์ Event

- รองรับไฟล์ภาพนิ่ง JPEG, PNG, WebP ขนาดไม่เกิน 10 MB และ PDF ขนาดไม่เกิน 50 MB
- ปฏิเสธ SVG, GIF, video และไฟล์ชนิดอื่นที่ไม่อยู่ในรายการรับรอง
- ไฟล์ถูกจัดเก็บผ่าน MinIO/S3-compatible storage ในทุก Environment
- สิทธิ์การเข้าถึงไฟล์ต้องสอดคล้องกับการเผยแพร่/การเข้าถึง Event และบทบาทผู้ใช้

## Reservation และการหมดอายุ

- Customer สร้าง reservation ได้ตาม inventory ที่ยังขายได้
- Reservation ที่ยังไม่ชำระถือสิทธิ์ใน inventory เป็นเวลา 15 นาที
- เวลาหมดอายุต้องเริ่มจากเวลาที่ระบบสร้าง reservation; หลังพ้นกำหนดโดยยังไม่ชำระ reservation หมดอายุและ inventory กลับมาใช้ได้
- การชำระเงินที่ยืนยันสำเร็จภายในเวลาที่กำหนดเปลี่ยน reservation เป็น booking ที่ชำระแล้ว
- คำขอซ้ำหรือเหตุการณ์แข่งกันต้องไม่ทำให้ขายเกิน capacity, จองที่นั่งเดียวซ้ำ หรือเปลี่ยน reservation เดียวให้เกิดผลชำระมากกว่าหนึ่งครั้ง
- ใช้กลไกเวลาแบบควบคุมได้ในการทดสอบ ไม่ต้องรอ 15 นาทีจริง

## Mock payment ผ่าน QR

- สำหรับ reservation ที่รอชำระ UI แสดง QR Code ที่เปิด URL หน้าธุรกรรมเดียวกันบนมือถือ
- หน้าธุรกรรมแสดงจำนวนเงินที่ต้องชำระ; Customer กรอกจำนวนเงินและต้องตรงกับยอดที่กำหนดก่อนยืนยัน
- เมื่อยอดตรงและยืนยันภายในช่วงเวลาจอง ระบบบันทึกผลการชำระ mock และเปลี่ยน booking เป็นชำระแล้ว
- ยอดไม่ตรง, reservation หมดอายุ, booking ที่ถูกยกเลิก และการยืนยันซ้ำต้องไม่ทำให้เกิดการชำระสำเร็จเพิ่มเติม
- มี bypass/mock สำหรับ automated test โดยไม่เชื่อม payment provider จริง; รายละเอียดวิธีเปิดใช้และป้องกันไม่ให้ถูกใช้โดย Customer ทั่วไปต้องกำหนดใน Plan

## Event cancellation และ refund status

- Event Owner ผู้สร้างเท่านั้นยกเลิก Event ได้
- เมื่อยกเลิก booking ทุกใบที่ชำระแล้วเข้าสู่สถานะ “รอคืนเงิน”
- Event Owner เปลี่ยนสถานะแบบ Manual ตามลำดับ “รอคืนเงิน” → “กำลังดำเนินการคืนเงิน” → “คืนเงินแล้ว”; ไม่มีระบบภายนอกหรือ payment provider เชื่อมต่อ
- ระบบบันทึกสถานะปัจจุบันและแสดงในมุมมองของ Event Owner; ข้อมูล audit เพิ่มเติม เช่น ผู้เปลี่ยนและเวลา เป็นข้อเสนอเพื่อยืนยันในคำถามเปิด
- ผลต่อ reservation ที่ยังไม่ชำระใน Event ที่ถูกยกเลิกยังไม่ระบุและต้องตอบก่อนยอมรับ Specification

## Dashboard

Dashboard แสดงข้อมูลของ Event Owner สำหรับ Event ที่ตนสร้าง อย่างน้อย:

- ความจุรวมที่เปิดขาย, จำนวนที่ยังไม่ขาย/ไม่ถูกจอง และจำนวน reserved/capacity
- จำนวน booking ที่ชำระแล้ว
- จำนวน booking ที่รอชำระ
- จำนวน reservation ที่หมดเวลา
- จำนวน booking ตามสถานะคืนเงินเมื่อ Event ถูกยกเลิก

ตัวเลขต้องสอดคล้องกับ inventory และสถานะจริง ไม่รวมการวิเคราะห์แนวโน้มหรือกราฟขั้นสูงใน MVP

## ขอบเขต UI และเทคโนโลยี

- Frontend ใช้ Next.js และ Tailwind CSS; Backend ใช้ NestJS; ฐานข้อมูลใช้ PostgreSQL
- UI ต้องรองรับเส้นทางผู้ใช้ที่ระบุและเชื่อมกับ API จริง ไม่ใช่หน้าจอ static mock
- เลือก CSS component library ที่เรียบง่ายหลังเปรียบเทียบตัวเลือกที่เข้ากับ stack ใน Plan; ใช้ lucide-icon และไม่ใช้ emoji เป็นของตกแต่ง
- MinIO/S3-compatible storage ต้องพร้อมใช้ในทุก Environment; วิธีแยก config/ข้อมูล Environment กำหนดใน Plan
- Package manager, monorepo tooling, deployment และ architecture รายละเอียดเป็นการตัดสินใจใน Plan ไม่ใช่ข้อกำหนดที่ล็อกไว้ใน Specification นี้

## แนวทางทดสอบและเกณฑ์ยอมรับ

### เส้นทางการใช้งาน

1. Owner สมัคร/เข้าสู่ระบบใน Owner realm, สร้าง Draft Event, เพิ่มรายละเอียดและไฟล์ที่รองรับ, เลือกผังหรือประเภทตั๋ว, กำหนด capacity/ราคา และ Publish ได้
2. Owner แก้คำอธิบาย/รูปภาพหลัง Publish ได้ แต่แก้ราคา, capacity, ที่นั่ง, ผัง หรือประเภทที่กระทบการจองไม่ได้
3. Customer login ใน Customer realm, เรียกดู Event ที่เผยแพร่, จองที่นั่งหรือจำนวนตั๋ว และเห็น QR/หน้าธุรกรรมได้
4. การกรอกยอดถูกต้องและยืนยันภายใน 15 นาทีทำให้ booking สำเร็จ; ยอดไม่ตรงหรือหมดเวลาไม่ทำให้สำเร็จ
5. เมื่อ reservation หมดอายุ inventory กลับมาเปิดจอง และ Dashboard สะท้อนการเปลี่ยนสถานะ
6. Owner เห็นตัวเลข Dashboard ที่ตรงกับข้อมูลจอง และบัญชี Owner อื่นเข้า Event/API นี้ไม่ได้
7. ผู้สร้างยกเลิก Event ได้; Owner คนอื่นและ Customer ยกเลิกไม่ได้; paid bookings เปลี่ยนและเดินสถานะคืนเงินตามลำดับ Manual

### ความถูกต้องภายใต้การแข่งขัน

- รันคำขอจองพร้อมกัน 100 รายการกับ inventory 20 หน่วยใน PostgreSQL จริง ทดสอบแยกโหมดระบุที่นั่งและแบบจำนวน
- ยืนยันว่ามี reservation ที่ถือสิทธิ์ inventory ได้ไม่เกิน 20, ไม่มีการจองที่นั่งซ้ำ, ไม่มี capacity ติดลบ และผลรวมสถานะตรงกับ inventory
- ทดสอบการแข่งขันระหว่างการชำระกับการหมดอายุ และการยืนยันชำระซ้ำ
- ตัวเลขนี้เป็น correctness baseline ระดับ R&D ไม่ใช่ throughput/latency SLO หรือ production load claim

### การตรวจสอบไฟล์และสิทธิ์

- ยอมรับ JPEG/PNG/WebP ขนาดไม่เกิน 10 MB และ PDF ไม่เกิน 50 MB; ปฏิเสธไฟล์ใหญ่เกินและ SVG/GIF/video/ชนิดที่ไม่รองรับ
- ทดสอบ API authorization โดยใช้บัญชีผิดบทบาท, Owner ที่ไม่ใช่ผู้สร้าง และ Customer ต่อ resource ที่ต้องจำกัดสิทธิ์
- ทดสอบว่า API ปฏิเสธการแก้ข้อมูลต้องล็อกหลัง Publish แม้เรียก API โดยตรง

## ประเด็นเสนอใน Specification ให้ผู้พัฒนาพิจารณา

- เมื่อยกเลิก Event ให้ยกเลิก reservation ที่ยังไม่ชำระทันทีและคืน inventory; paid bookings เดินตาม workflow คืนเงิน Manual
- แยก identity ของ Google ภายในระบบ Owner และ Customer โดยเด็ดขาด แม้อีเมล Google ตรงกันก็ไม่ใช้บัญชีหรือ session ร่วมกัน
- บันทึกผู้เปลี่ยนสถานะคืนเงินและเวลา เพื่อให้ตรวจสอบการทำงาน Manual ได้
- กำหนดข้อมูล Event ขั้นต่ำก่อน Publish เป็นชื่อ, คำอธิบาย, วันเวลา, โหมดขาย, ผังหรือ capacity/ประเภทตั๋ว, ราคา และไฟล์ประกอบอย่างน้อยหนึ่งรายการหรือไม่ (ต้องยืนยันว่าไฟล์จำเป็นหรือไม่)

เมื่อผู้พัฒนายอมรับ Specification นี้แล้ว จึงจัดทำ Implementation Plan แยกต่างหากพร้อมโครงสร้าง repository, ลำดับ build, trade-offs และคำสั่งตรวจสอบของ stack ที่เลือก.
